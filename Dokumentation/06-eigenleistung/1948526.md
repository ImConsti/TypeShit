# Eigenleistung – Matrikelnummer: 1948526

## Funktionen: Aufgaben lesen & erstellen + Middleware

## 1. Beschreibung der Funktion

In meinem Teilprojekt habe ich das Lesen und Erstellen von Aufgaben sowie deren spezifische Absicherung der API umgesetzt.

Aus Nutzersicht bedeutet das: Nach dem erfolgreichen Login, lädt das Dashboard über die API ausschließlich die eigenen TODOs. 
Möchte ein Nutzer neue Aufgaben hinzufügen, kann er diese über das TaskInput-Formular auf der Hauptseite anlegen. 
Hier muss der Nutzer einen Titel (bis max. 300 Zeichen) angeben. Optional kann eine detaillierte Beschreibung (bis max. 5000 Zeichen), 
die Priorität (Hoch, Mittel, Niedrig) und ein Fälligkeitsdatum ab dem Tag der Erstellung angegeben werden.
 Durch einen einfachen Klick auf den "Hinzufügen"-Button werden die eingegeben Daten zu einem neuen TODO.
Um das UI dynamisch/responsiv zu gestalten und eine gute UX zu gewährleisten, wurde folgendes Live-Feedback und Micro-Interactions eingebaut: 

 - Die Elemente wachsen und schrumpfen dynamisch und im Verhältnis zueinander mit der Fenstergröße.

 - Fokus-Hervorhebung bei Eingabefeldern: Klickt der Nutzer in ein Textfeld, bekommt dieses nicht einfach nur einen harten Rahmen. Durch einen sanft animierten Übergang färbt sich der Rahmen blau und es entsteht ein leichter, blauer Leuchteffekt. So ist immer klar, welches Feld gerade aktiv ist.

 - Haptisches Button-Feedback: Der Submit-Button wirkt nicht flach, sondern reagiert physisch auf den Nutzer. Beim Darüberfahren mit der Maus (Hover) hebt er sich minimal an und ändert seine Hintergrundfarbe. Klickt man ihn an, drückt er sich optisch leicht ein und wird minimal kleiner, was ein sehr befriedigendes Klick-Gefühl erzeugt. 

 - Live-Validierung durch Zeichenzähler: Unter den Textfeldern läuft ein Zeichenzähler in Echtzeit mit. Nähert sich der Nutzer dem Limit (z.B. ab 290 von 300 Zeichen beim Titel), schlägt der Zähler visuell an und färbt sich automatisch rot, um rechtzeitig vor einem Abbruch zu warnen

 - Interaktive Dropdowns & Icons: Das Select-Feld für die Priorität wurde mit einem eigenen SVG-Pfeil versehen, der beim Hovern seine Farbe passend zum Primär-Blau der App ändert. Auch das kleine Kalender-Icon im Datumsfeld reagiert auf Mausberührungen und wird deutlich sichtbarer, um die Klickbarkeit zu signalisieren.

 - Barrierefreie Skalierung: Bei den Schriftgrößen kommen relative Maßeinheiten (rem) zum Einsatz. Das bedeutet: Wenn ein Nutzer in seinen Systemeinstellungen eine größere Standardschrift benötigt, wächst die Schrift in der App automatisch und proportional mit, ohne das Layout zu zerstören.

Im Backend habe ich die beiden Endpunkte GET /api/tasks und POST /api/tasks sowie die zentrale authenticateToken-Middleware umgesetzt.
Der GET-Endpunkt liefert nach erfolgreicher Authentifizierung ausschließlich die Aufgaben des aktuell eingeloggten Users. Dazu wird aus dem verifizierten JWT die User-ID ausgelesen und die Datenbankabfrage entsprechend gefiltert. So sieht jeder Nutzer nur seine eigenen TODOs und kann nicht auf fremde Daten zugreifen.
Der POST-Endpunkt nimmt die vom Frontend gesendeten Daten entgegen und legt eine neue Aufgabe an. Hier greift eine serverseitige Validierung: Der Titel ist Pflicht und darf maximal 300 Zeichen lang sein, die Beschreibung maximal 5000 Zeichen. Das Fälligkeitsdatum wird, falls mitgeschickt, ebenfalls geprüft, sodass keine Vergangenheit möglich ist. Nur wenn alle Prüfungen erfolgreich sind, wird die Aufgabe in der Datenbank gespeichert und mit einer eindeutigen ID an das Frontend zurückgegeben. Schlagen diese Validierungen aufgrund fehlerhafter Eingaben fehl, wird die Anfrage direkt mit dem HTTP-Statuscode 400 Bad Request abgelehnt.
Beide Endpunkte sind durch die authenticateToken-Middleware abgesichert. Diese liest den Bearer-Token aus dem Authorization-Header, verifiziert ihn und hängt die User-Informationen an das Request-Objekt. Fehlt der Token, wird die Anfrage mit 401 Unauthorized abgewiesen. Ist der Token ungültig oder abgelaufen, antwortet der Server mit 403 Forbidden. Die Middleware ist bewusst zentral gehalten, damit sie von allen geschützten Routen des Projekts wiederverwendet werden kann und nicht in jeder Route einzeln implementiert werden muss.
Durch die Kombination aus Frontend-Formular (mit Live-Feedback und clientseitiger Validierung) und den abgesicherten Backend-Endpunkten entsteht ein durchgängiger, sicherer und nutzerfreundlicher Ablauf vom Anlegen einer Aufgabe bis zu ihrer Anzeige im Dashboard.

## 4. Zugrundeliegende Ideen & Funktionsweise

- Laden der Daten (useEffect): Die Aufgaben werden im TasksPanel nur beim ersten Aufruf der Seite vom Server geladen. Dafür wird ein useEffect-Hook mit einem leeren Array [] verwendet, um zu verhindern, dass React nach dem Setzen der Daten in eine Endlosschleife gerät, was während Tests vor dem Commit passiert ist.

- Aktualisierung der Aufgabenliste: Beim Hinzufügen von neuen Todos wird der alte State einbezogen (setTasks((prev) => [savedTask, ...prev])). Dadurch wird die neue Aufgabe einfach ganz oben an das bestehende Array angehängt, und das UI aktualisiert sich, ohne dass die Seite neu geladen werden muss.

- Absicherung durch Tokens: Die Backend-Routen sind über eine zentrale Middleware geschützt. Diese liest den Authorization-Header aus, trennt das "Bearer"-Präfix ab (split(' ')[1]) und überprüft den JWT-Token. Erst wenn der Token gültig ist, wird die decodierte userId an das Request-Objekt angehängt und der Request an die eigentliche Datenbankabfrage weitergeleitet. Die Middleware stellt sicher, dass die `userId` ausschließlich aus dem verifizierten Token kommt und nie aus dem Request-Body. Dadurch wird verhindert, dass ein Nutzer durch manipulierte Anfragen auf fremde Aufgaben zugreifen oder diese erstellen kann

- Konsistente Datumsverarbeitung: Da reine Datumsvergleiche beim Speichern zu ungewollten Tagesverschiebungen führen können, wird der lokale Zeitzonen-Offset explizit mit einbezogen. Dies garantiert, dass das vom Nutzer gewählte Fälligkeitsdatum exakt und ohne Abweichungen in die Datenbank übernommen wird. Diese Methode sichert das im Kalender keine Tage in der Vergangenheit mehr ausgewählt werden können. 

- Eingabevalidierung im Backend: Bevor eine neue Aufgabe über die POST-Route gespeichert wird, prüft der Endpunkt sofort, ob die Eingaben gültig sind (z. B. ob die erlaubten Zeichenlimits für Titel und Beschreibung eingehalten wurden). Fehlerhafte Anfragen werden direkt mit dem passenden HTTP-Statuscode abgelehnt.

## 5. Getroffene Entscheidungen

Clientseitige vs. Serverseitige Validierung (Redundanz): Die doppelte Validierung (Frontend + Backend) ist eine bewusste Architektur-Entscheidung. Das Frontend validiert für eine optimale UX (sofortiges Feedback z.B. per Zeichenzähler oder Kalender-Blockade). Das Backend validiert streng nach dem "Never trust the client"-Prinzip, um die Datenbank-Integrität zu schützen und manipulierte API-Requests konsequent abzufangen.

Zentrale Middleware: Die Token-Prüfung wurde bewusst nicht in jeder Route einzeln implementiert, sondern als zentrale Middleware in der index.ts ausgelagert. Dies folgt dem DRY-Prinzip (Don't Repeat Yourself), hält den Code der einzelnen Routen schlank und stellt sicher, dass das Team einen standardisierten Auth-Guard für alle weiteren Endpunkte nutzen kann.

Zeichenbeschränkung der Titel und Beschreibung: Ich habe mich für diese harten Limits entschieden, um das System auf mehreren Ebenen abzusichern. Im Backend schütze ich den Server durch zu große Payloads. Im Frontend schützt das Limit mein responsives Layout vor unkontrollierten Overflows und zwingt den Nutzer aus UX-Sicht dazu, den Titel wirklich nur als kurze Zusammenfassung und die Description für die eigentlichen Details zu nutzen.

Textarea statt Input: Für Titel und Beschreibung habe ich mich zum Schluss doch gegen ein einzeiliges input und für ein textarea entschieden. Ein normales Textfeld erzwingt eine starre Zeile und bricht längere Texte unkontrolliert um oder schneidet sie optisch ab. Bei längeren Beschreibungen oder Titeln war das aus UX-Sicht sehr umständlich und ineffizient. Mit textarea kann der Nutzer nun mehrzeilig tippen, der Inhalt bleibt lesbar und das Layout bleibt stabil. Gleichzeitig bleibt die Höhe über CSS begrenzt, sodass das Formular nicht „auseinanderläuft“. Das passt zur restlichen UX-Strategie: klare Eingabe, kontrolliertes Layout und trotzdem genug Platz für echte Inhalte.

Flex-Layout im TaskInput: Im Formular habe ich bewusst `display: flex` mit `flex-wrap: nowrap` und unterschiedlichen Flex-Werten (`.flex2` für den Titel, `.flex3` für die Beschreibung) verwendet. Dadurch bekommt die Beschreibung mehr Platz als der Titel, und auf Desktop bleiben alle Elemente (Titel, Beschreibung, Priorität, Datum, Button) in einer Zeile. Das verhindert unnötige Umbrüche und hält das Formular kompakt, während die Eingabefelder trotzdem proportional wachsen können.

Strikte TypeScript-Typisierung: Ich habe konsequent darauf geachtet, den Datentyp any zu vermeiden und stattdessen mit festen Interfaces und Event-Typen zu arbeiten. Dadurch sind die Datenstrukturen klar definiert. Fehler fallen so direkt beim Programmieren auf und verursachen später keine unerwarteten Abstürze im Browser, was die Anwendung insgesamt deutlich stabiler macht.
