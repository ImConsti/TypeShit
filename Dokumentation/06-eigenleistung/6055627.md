## 1. Beschreibung der Funktion

Die Statistik-Seite gibt dem angemeldeten Benutzer einen Überblick über seine Aufgabendaten. Statt statischer Demo-Werte lädt die finale Implementierung die tatsächlichen Daten des Benutzers aus dem Backend und berechnet daraus die angezeigten Statistiken.

Die Seite zeigt aktuell:

- die Gesamtanzahl aller Aufgaben,
- die Anzahl erledigter Aufgaben,
- die Anzahl offener Aufgaben,
- die Anzahl wichtiger Aufgaben,
- die Anzahl aufeinanderfolgender Tage mit mindestens einer erledigten Aufgabe (**Streak**),
- eine Tabelle der offenen Aufgaben mit Priorität und Fälligkeitsdatum,
- eine Liste wichtiger Aufgaben,
- eine visuelle Statusverteilung, zwischen Balkenansicht und Kreis-/Donut-Ansicht umschaltbar,
- überfällige Aufgaben sowie Aufgaben, die innerhalb der nächsten sieben Tage fällig werden.

Die Statistik-Seite ist als eigene Route unter `/statistics` erreichbar. Sie dient als analytische Ansicht derselben Aufgabendaten, die in der normalen Aufgabenverwaltung bearbeitet werden.

Screenshots der beiden Statusdarstellungen befinden sich unter:

- `screenshots/statistics-balken.png`
- `screenshots/statistics-kreis.png`
- `screenshots/statistiken.png`

## 2. Einbindung in das Gesamtprojekt

Die Statistik-Funktion verbindet Frontend, Authentifizierung, Backend-API und PostgreSQL-Datenbank miteinander.

### Frontend

Die relevanten Frontend-Dateien sind:

- `frontend/src/app/statistics/page.tsx`
  - lädt die Statistikdaten vom Backend,
  - liest das JWT aus `localStorage`,
  - sendet den Token im `Authorization`-Header,
  - behandelt Lade- und Fehlerzustände,
  - übergibt die geladenen Daten an die Darstellungskomponente.

- `frontend/src/app/components/StatisticsPage.tsx`
  - definiert die TypeScript-Struktur der API-Antwort (`StatisticsData`),
  - rendert sämtliche Statistiken,
  - berechnet die Prozentwerte für die Statusvisualisierung,
  - ermöglicht den Wechsel zwischen Balken- und Kreis-/Donut-Ansicht,
  - zeigt offene Aufgaben, wichtige Aufgaben und bevorstehende Fälligkeiten an.

- `frontend/src/app/components/StatisticsPage.module.css`
  - enthält das Styling des Statistik-Dashboards,
  - enthält die CSS-basierte Donut-Darstellung,
  - enthält Styles für den kombinierten Balken, die Deadline-Liste und das responsive Layout.

### Backend

Die Backend-Logik der Statistik befindet sich in:

- `backend/src/index.ts`
  - `GET /api/statistics`
  - JWT-Prüfung über die vorhandene Middleware `authenticateToken`,
  - benutzerspezifische Datenbankabfragen mit Drizzle ORM,
  - Berechnung der Zusammenfassungswerte, des Streaks und der Deadline-Informationen.

### Datenfluss

Der finale Datenfluss sieht folgendermaßen aus:

```text
Angemeldeter Benutzer
      |
      v
Frontend /statistics
      |
      | GET /api/statistics
      | Authorization: Bearer <JWT>
      v
Express-Backend
      |
      | verifizierte userId aus dem JWT
      v
Drizzle ORM
      |
      +----> users-Tabelle
      |
      +----> tasks-Tabelle
      |
      v
Berechnung der Statistikwerte
      |
      v
JSON-Antwort
      |
      v
StatisticsPage.tsx
```

Die `userId` wird niemals aus einem Query-Parameter oder aus dem Request-Body übernommen. Sie stammt ausschließlich aus dem verifizierten JWT. Dadurch kann ein Benutzer nur die Statistiken seiner eigenen Aufgaben abrufen.

## 4. Backend-Implementierung

### 4.1 Authentifizierung und Benutzertrennung

Der Endpunkt ist durch die vorhandene Middleware `authenticateToken` geschützt:

```ts
app.get('/api/statistics', authenticateToken, async (req, res) => {
  const userId = req.user!.userId;
  // ...
});
```

Die Middleware überprüft das JWT, bevor der eigentliche Endpunkt ausgeführt wird. Der dekodierte Token enthält unter anderem die `userId`, die E-Mail-Adresse und die Rolle des Benutzers. Der Statistik-Endpunkt vertraut daher keiner vom Client frei übergebenen Benutzer-ID.

Diese Entscheidung ist sicherheitsrelevant, weil ein Request wie

```text
/api/statistics?userId=5
```

sonst theoretisch dazu führen könnte, dass ein Client die Statistik eines anderen Benutzers anfordert. Durch die Verwendung der verifizierten `userId` aus dem JWT wird dieses Problem vermieden.

### 4.2 Datenbankabfragen mit Drizzle ORM

Das Backend lädt sowohl die Aufgaben des Benutzers als auch dessen Benutzerdatensatz:

```ts
const [userTasks, userRows] = await Promise.all([
  db.select().from(tasks).where(eq(tasks.userId, userId)),
  db.select().from(users).where(eq(users.id, userId)),
]);
```

Mit `Promise.all` können beide voneinander unabhängigen Datenbankabfragen parallel ausgeführt werden.

Die Aufgabenabfrage wird über `tasks.userId` gefiltert. Dadurch basieren alle weiteren Berechnungen ausschließlich auf den Daten des authentifizierten Benutzers.

### 4.3 Berechnung der Zusammenfassung

Der Endpunkt bildet aus dem Aufgaben-Array die benötigten Gruppen:

```ts
const finishedTasks = userTasks.filter((task) => task.isDone === true);
const openTasks = userTasks.filter((task) => task.isDone === false);
const importantTasks = userTasks.filter((task) => task.priority === 'Hoch');
```

Die daraus erzeugte Zusammenfassung enthält:

```ts
summary: {
  totalTasks: userTasks.length,
  finished: finishedTasks.length,
  inProgress: openTasks.length,
  important: importantTasks.length,
  streakDays: ...
}
```

Im finalen Datenbankschema existiert für Aufgaben kein Feld `pinned`. Deshalb wird innerhalb der Statistik-Funktion eine Aufgabe mit der Priorität `Hoch` einheitlich als wichtige Aufgabe behandelt.

### 4.4 Berechnung des Streaks

Der Streak beschreibt die Anzahl aufeinanderfolgender Tage, rückwärts vom heutigen Tag gezählt, an denen mindestens eine Aufgabe erledigt wurde.

Relevant sind nur Aufgaben mit einem gültigen `doneAt`-Zeitstempel. Deren Abschlussdaten werden in einen stabilen Schlüssel im Format `YYYY-MM-DD` umgewandelt und in einem `Set` gespeichert. Ein `Set` wird verwendet, weil mehrere erledigte Aufgaben am selben Tag trotzdem nur als ein aktiver Tag zählen sollen.

Der Algorithmus beginnt beim heutigen Tag und geht anschließend jeweils einen Tag zurück:

```ts
while (completionDays.has(utcDateKey(currentDay))) {
  streakDays += 1;
  currentDay = addUtcDays(currentDay, -1);
}
```

Hat ein Benutzer zum Beispiel heute, gestern und vorgestern jeweils mindestens eine Aufgabe erledigt, beträgt der Streak `3`. Wurde heute noch keine Aufgabe erledigt, beträgt der aktuelle Streak `0`.

### 4.5 Datums- und Zeitzonenbehandlung

Die Anwendung verwendet:

```ts
const APP_TIME_ZONE = 'Europe/Berlin';
```

Datumswerte werden bewusst normalisiert, da ein Server beispielsweise in UTC laufen kann, während sich der Benutzer in der deutschen Zeitzone befindet. Hilfsfunktionen erzeugen stabile Datumsschlüssel und verhindern dadurch unbeabsichtigte Verschiebungen um einen Kalendertag, insbesondere in der Nähe von Mitternacht.

Der angezeigte Wochentag und das Datum werden auf Deutsch formatiert, zum Beispiel:

```text
Donnerstag
11. Juni 2026
```

### 4.6 Offene und wichtige Aufgaben

Der Endpunkt reduziert die vollständigen Datenbankdatensätze auf die Strukturen, die das Frontend tatsächlich benötigt:

```ts
openTasks: openTasks.map((task) => ({
  title: task.title,
  priority: task.priority,
  due: task.dueDate ?? '',
})),

importantTasks: importantTasks.map((task) => task.title),
```

Dadurch bleibt die API-Antwort übersichtlich und es werden keine unnötigen Datenbankfelder an das Frontend übertragen.

## 5. Frontend-Implementierung

### 5.1 Laden der realen Statistikdaten

Die Route `/statistics` liest den gespeicherten Authentifizierungstoken und ruft damit das Backend auf:

```ts
const token = localStorage.getItem('auth_token');

const response = await fetch(
  `${API_BASE}/api/statistics`,
  {
    method: 'GET',
    headers: {
      Authorization: `Bearer ${token}`,
      'Content-Type': 'application/json',
    },
  }
);
```

Die Basis-URL stammt aus:

```text
NEXT_PUBLIC_API_URL
```

Für die lokale Entwicklung wird `http://localhost:3001` als Fallback verwendet.

Die Komponente besitzt getrennte Zustände für:

- den Ladevorgang,
- erfolgreich geladene Statistikdaten,
- Fehler beim Request.

Dadurch wird bei einem fehlgeschlagenen Backend-Aufruf nicht stillschweigend wieder auf alte Demo-Werte zurückgegriffen.

### 5.2 TypeScript-Datenvertrag

Das Interface `StatisticsData` definiert den Vertrag zwischen Frontend und Backend. Die von `/api/statistics` zurückgegebene JSON-Struktur muss diesem Interface entsprechen.

Das aktuelle Interface enthält unter anderem:

```ts
interface StatisticsData {
  user: { ... };
  summary: { ... };
  openTasks: Task[];
  importantTasks: string[];
  upcomingDeadlines: UpcomingDeadline[];
}
```

Die Verwendung von TypeScript reduziert Integrationsfehler, weil fehlende oder umbenannte Felder der API-Antwort bereits während der Entwicklung erkannt werden können.

### 5.3 Statusvisualisierung

Das Frontend berechnet die Prozentwerte aus der vom Backend gelieferten Zusammenfassung:

```ts
const finishedPercent = asPercent(
  stats.summary.finished,
  stats.summary.totalTasks
);
```

Der Benutzer kann zwischen zwei Darstellungen wechseln:

1. **Balkenansicht** – zeigt erledigte und offene Aufgaben gemeinsam in einem horizontalen Balken mit Legende.
2. **Kreis-/Donut-Ansicht** – zeigt dieselbe Verteilung kreisförmig und stellt die Gesamtanzahl der Aufgaben in der Mitte dar.

Der ausgewählte Darstellungsmodus wird über folgenden State gesteuert:

```ts
const [statusView, setStatusView] = useState<'bars' | 'circles'>('bars');
```

Beide Ansichten sind somit lediglich unterschiedliche Darstellungen derselben zugrunde liegenden Statistikdaten und verwenden keine getrennte Berechnungslogik.

Das Backend erzeugt inzwischen `upcomingDeadlines` aus offenen Aufgaben, die ein Fälligkeitsdatum besitzen. Für jede Aufgabe werden unter anderem berechnet:

- das Fälligkeitsdatum,
- die Anzahl der Tage bis zum Fälligkeitsdatum,
- ob die Aufgabe bereits überfällig ist,
- eine deutsch formatierte Datumsanzeige.

Das konfigurierte Zeitfenster beträgt:

```ts
const DEADLINE_WINDOW_DAYS = 7;
```

Das Ergebnis enthält überfällige Aufgaben sowie Aufgaben, die innerhalb der nächsten sieben Tage fällig sind. Die Einträge werden nach `daysUntil` sortiert.

Das Frontend zeigt dazu beispielsweise folgende Beschriftungen:

```text

```

Durch diese spätere Teamänderung wurde im finalen `StatisticsData`-Vertrag das bisherige Feld `weeklyCompletion` ersetzt durch:

```ts
upcomingDeadlines: UpcomingDeadline[];
```

## 7. Wichtige Designentscheidungen

### Berechnung im Backend statt im Frontend

Die finale Lösung berechnet die Statistikwerte serverseitig, anstatt sämtliche rohen Aufgabendatensätze an die Statistik-Seite zu senden und dort im Browser auszuwerten.

Vorteile:

- zentrale und einheitliche Umsetzung der Geschäftslogik,
- kleinerer und klarer definierter API-Vertrag,
- Benutzerfilterung erfolgt bereits, bevor Daten das Backend verlassen,
- das Frontend konzentriert sich hauptsächlich auf die Darstellung,
- mögliche zukünftige Clients könnten denselben Endpunkt wiederverwenden.

### Benutzer-ID aus dem JWT

Die Benutzer-ID stammt aus dem verifizierten JWT und nicht aus frei übergebenen Request-Parametern. Diese Entscheidung wurde aus Sicherheitsgründen und zur sauberen Trennung der Benutzerdaten getroffen.

### Hohe Priorität als Definition für „wichtig“

Im Projekt wurden ursprünglich unterschiedliche Möglichkeiten diskutiert, wichtige Aufgaben zu kennzeichnen. Im finalen Aufgaben-Schema steht `pinned` nicht zur Verfügung. Deshalb wird einheitlich `priority === 'Hoch'` verwendet.

### Keine externe Chart-Bibliothek für die Donut-Ansicht

Für die Kreisansicht wird CSS verwendet, anstatt eine zusätzliche Visualisierungsbibliothek einzubinden. Für die relativ einfache Verteilung zwischen erledigten und offenen Aufgaben bleibt die Implementierung dadurch leichtgewichtig.

### Bevorstehende Deadlines statt Wochenfortschritt

In der finalen Teamiteration wurde der Wochenfortschritt durch eine Liste bevorstehender Deadlines ersetzt. Dadurch erhält der Benutzer unmittelbar handlungsrelevante Informationen, insbesondere weil überfällige Aufgaben direkt sichtbar sind.

## 9. Fehlerbehandlung

Die Statistik-Integration behandelt Fehler sowohl im Backend als auch im Frontend.

Beispiele im Backend:

- `401`, wenn kein Token mitgesendet wurde,
- `403`, wenn der Token nicht verifiziert werden kann,
- `404`, wenn der authentifizierte Benutzer nicht mehr existiert,
- `500` bei unerwarteten Datenbank- oder Verarbeitungsfehlern.

Verhalten im Frontend:

- während der Anfrage wird ein Ladezustand angezeigt,
- bei einem fehlgeschlagenen Request wird eine verständliche Fehlermeldung dargestellt,
- bei einem Fehler werden keine veralteten Demo-Statistiken anstelle der realen Daten angezeigt.
